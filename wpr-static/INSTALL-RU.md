# Static Site Generator for WordPress — WPR Static 1.1.0

## Основной сценарий: статический фронтенд на текущем домене

1. Сделайте резервную копию сайта и проверьте плагин на staging.
2. Установите ZIP стандартным способом. При наличии версии 1.0.0 обновите её поверх старой; slug и настройки не меняются.
3. Откройте **Static Site Generator** в меню WordPress. Нажмите **«Включить статический режим»**. Адрес текущего сайта подставляется автоматически.
4. Дождитесь завершения генерации и проверки. На главной странице плагина появятся фактическое число подготовленных маршрутов и настроенный режим выдачи.
5. Проверьте сайт в приватном окне без cookies. В инструментах разработчика, Network → заголовки ответа, ищите `X-WPR-Static: apache`, `early-php` или `wordpress-php`. Если заголовка нет, запрос обработан WordPress или другим слоем кеширования.
6. Проверьте вход в админку, страницы с формами, поиск, редиректы, удаление и закрытие публичной записи, автообновление после сохранения записи. Проверьте выдачу с cookies и параметрами запроса.
7. Для отключения используйте «Выключить статический режим» либо обычную деактивацию плагина. Плагин удаляет только собственные правила и drop-in; исходный WordPress не перемещается.

### Автоматический выбор способа выдачи

- **Apache:** при установке WordPress в корне веб-директории, доступных mod_rewrite/mod_headers, стандартной конфигурации и правах записи плагин добавляет собственный блок `.htaccess`. До копирования HTML проверяет реальным HTTP-запросом доступность внутреннего маршрута и запрет прямого доступа к выделенному каталогу. После копирования проверяет один HTML-маршрут. При неуспехе правила удаляются, выполняется переход к PHP. Unicode и нестандартные пути используют PHP.
- **Ранний PHP:** собственный `wp-content/advanced-cache.php` и при необходимости маркированный блок `WP_CACHE` в стандартном `wp-config.php`. Чужие drop-in и явное значение `WP_CACHE=false` не перезаписываются. При недоступности файлов остаётся резервная выдача через WordPress.
- **Резервный WordPress PHP:** отдача из готового файла после загрузки ядра и маршрутизации WordPress. Не обещает отсутствие обращения к БД. На хостинге с конфликтующим `advanced-cache.php` включение статического режима блокируется.

При прямом режиме хранится отдельная управляемая копия только подходящих HTML-страниц в защищённом каталоге `.wpr-static-front-*` под корнем WordPress. Не переносите этот каталог на другой сервер; перед сменой веб-сервера/конфигурации отключите статический режим. Служебные данные сборки остаются в приватном хранилище.

### Обновление страниц

После изменения контента, статуса записи, меню, таксономий, темы и ряда настроек выдача временно возвращается к WordPress. Через примерно 60 секунд после последнего обнаруженного изменения начинается полная фоновая пересборка при работающем WP-Cron. Если изменение произошло во время генерации, устаревшая сборка не активируется. При выключенном автообновлении после изменения потребуется ручная пересборка. После успешной генерации сохраняются последние сборки фронтенда по установленному лимиту (по умолчанию 3), экспортные сборки автоматически не удаляются.

Если все страницы обслуживаются веб-сервером напрямую, WP-Cron может не запускаться без запросов к WordPress. Для стабильной работы на малопосещаемом сайте используйте планировщик хостинга или WP-CLI; на открытом экране плагина очередь также обрабатывается запросами администратора.

### Ограничения 1.1.0

- Статический режим обслуживает анонимные GET/HEAD-запросы без cookies и query string. Это намеренно консервативное решение для первого релиза: даже аналитические cookies приводят к динамической выдаче.
- POST-формы, страницы с nonce, Set-Cookie, private/no-store, CSP, X-Robots-Tag, непредсказуемым Vary и перенаправляемые маршруты остаются динамическими. GET-поиск уходит в WordPress по query string. Автоматическое определение всех динамических зависимостей невозможно; сайты с персонализацией, ограничениями доступа по IP/географии или сторонним кэшем необходимо отдельно проверять. WooCommerce live-режим заблокирован.
- HTML сохраняется в оригинальном виде; CSS, JS и изображения остаются на существующих URL, не копируются для live-выдачи. Оригинальные Sitemap, robots.txt и 404 обрабатывает WordPress/сервер. Не требуется менять SEO-поля или домен.
- ZIP для самостоятельного хостинга создаётся отдельной экспортной сборкой: «Создать сборку для ZIP». Live-сборки не являются переносимыми архивами.
- Прямые изменения базы данных, файлов темы, настройки сторонних сервисов/CDN, нестандартные хуки могут не вызвать автоинвалидацию. В таких случаях выполните ручную пересборку. Сторонний CDN может сохранять старые ответы независимо от WPR Static; очистите/отключите его до тестирования.
- Существуют конфигурации, где приватная рабочая директория вне web root недоступна для записи. В этом случае диагностика сообщит ошибку, а не создаст открытое хранилище. Администратор может настроить `WPR_STATIC_STORAGE`.

### Аварийное отключение

В штатном сценарии используйте кнопку отключения. Если интерфейс недоступен, деактивируйте плагин через WP-CLI: `wp plugin deactivate wpr-static`. При необходимости администратор хостинга может удалить только маркер `enabled` из управляемого каталога `.wpr-static-front-*` и `frontend-enabled` из приватного хранилища, убрать блок `# BEGIN WPR STATIC FRONTEND` … `# END WPR STATIC FRONTEND` из `.htaccess`. Не удаляйте чужие правила. Проверьте, что `advanced-cache.php` помечен `WPR STATIC OWNED DROPIN V1`, прежде чем удалить его; маркированный блок `WPR STATIC CACHE` из wp-config.php удаляется только если он принадлежит плагину.

### WP-CLI

```bash
wp wpr-static enable
wp wpr-static frontend
wp wpr-static rebuild
wp wpr-static disable
```

## Справка по переносимому ZIP-экспорту (из версии 1.0, дополнительно)

# WPR Static 1.0.0 — установка и проверка

**Статус:** первая реализация MVP, предназначенная для приёмки на staging. Не заменяет полноценное интеграционное и нагрузочное тестирование.

## Быстрый старт

1. Установите `wpr-static-v1.0.0.zip` через WordPress → Плагины → Добавить → Загрузить плагин. Активируйте.
2. Откройте WPR Static → Настройки. Укажите URL будущего сайта, например `https://static.example.com`. Для ZIP локальный путь не требуется.
3. Откройте «Диагностика» и устраните ошибки. PHP 8.1+, WP 6.2+, DOM/XML, ZipArchive, обычные постоянные ссылки и публичная главная страница обязательны. Multisite не поддерживается.
4. Нажмите «Сгенерировать сайт». Фоновая очередь использует WP-Cron и запросы открытой страницы администратора. На малопосещаемых сайтах нужен системный cron или WP-CLI.
5. После статуса `ready` откройте отчёт и проверьте предупреждения. Скачайте ZIP. Распакуйте его в отдельную директорию статического веб-сервера.
6. Настройте выдачу `index.html` для каталогов и `404.html` с HTTP-статусом 404. Проверьте сайт в браузере: меню, изображения, формы, шрифты, адаптивность, SEO. Не переключайте DNS до проверки.

## Настройка хранилища

По умолчанию создаётся приватная папка рядом с DOCUMENT_ROOT, вне WordPress. Если она недоступна для записи, подготовьте отдельный каталог, доступный PHP-пользователю, вне **всех** публичных корней сайтов, и добавьте в `wp-config.php`:

```php
define('WPR_STATIC_STORAGE', '/home/account/private/wpr-static');
```

Родительский каталог должен существовать. Не используйте `wp-content/uploads`. Если сервер обслуживает файлы из нескольких document root, проверьте отсутствие HTTP-доступа к хранилищу самостоятельно. WordPress CLI может иметь другой DOCUMENT_ROOT, поэтому для совместного использования CLI и веб-панели рекомендуется явно задать WPR_STATIC_STORAGE.

## Локальная публикация

По умолчанию разрешены выделенные каталоги внутри родительской папки WordPress, но не сам WordPress и не приватное хранилище. При необходимости явно задайте разрешённый родительский каталог:

```php
define('WPR_STATIC_PUBLISH_ROOT', '/home/account/static-sites');
```

Укажите в настройках конечную отдельную директорию, например `/home/account/static-sites/public`. Она должна быть пустой либо полностью управляться WPR Static. Не кладите туда сторонние файлы, `.htaccess`, конфиги или ресурсы вручную: публикация откажется перезаписывать изменённые/чужие файлы. Настройку веб-сервера делайте вне этой директории. При повторной публикации устаревшие управляемые файлы исчезают вместе с предыдущим деревом. Публикация — двухшаговое переименование каталогов, не гарантированно атомарное; краткий интервал недоступности возможен.

Если PHP был аварийно остановлен во время переключения, блок `PUBLISH_RECOVERY_REQUIRED` защищает от дальнейших публикаций. Администратор сервера должен проверить `wp option get wpr_static_publish_journal --format=json`, содержимое `dest`, `stage`, `backup`, восстановить предыдущую версию из backup при отсутствии dest, сверить файлы и реестр `wpr_static_destinations`; только затем удалить журнал командой `wp option delete wpr_static_publish_journal`. Не удаляйте backup до проверки. Автоматический мастер восстановления не реализован.

## WP-CLI

```bash
wp wpr-static doctor
wp wpr-static build
wp wpr-static status
wp wpr-static resume
wp wpr-static cancel
wp wpr-static validate
wp wpr-static export
wp wpr-static publish
```

Команды используют последнюю сборку и сохранённые настройки. `resume` продолжает активную/приостановленную очередь. Для больших архивов и локальной публикации рекомендуется CLI: эти операции пока синхронные, в веб-запросе действуют ограничения PHP.

## Границы

- Нет инкрементальной генерации, SFTP/S3/Git, динамического поиска, форм, авторизации, WooCommerce checkout, автоматического экспорта редиректов.
- HTML URL с query string и сайты с plain permalinks не поддерживаются. Внешние ресурсы не скачиваются. Версионные query ресурсов получают отдельное имя с хешем.
- Не гарантируется перенос arbitrary JavaScript, ES import graph, сложных CSS-экранирований или всех нестандартных lazy-loading атрибутов. Проверка — статическая, не браузерная.
- Источник должен возвращать настоящую 404 HTML-страницу. Неэкспортируемые ссылки сохраняются с предупреждением; критические ошибки ресурсов блокируют публикацию.
- Внутренние ресурсы, распознанные в HTML/CSS, должны иметь поддерживаемое расширение. Запрещённые и защищённые файлы не экспортируются, однако анонимно доступный сайт сам может содержать конфиденциальные данные — требуется проверка владельцем.
- История и артефакты удаляются вручную; очистка при удалении плагина намеренно не выполняется. Публикация не удаляется при удалении плагина.
- JSON-отчёт и манифест доступны администратору. CSV и TXT, отдельный интерфейс повторения failed tasks, расширенная локализация диагностических сообщений и автоматическая ротация сборок ещё не реализованы.
